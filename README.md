## 1 часть

#### Микрофронтенды

Поделить необходимо на изолированные бизнес сущности. Выделить можно
1. **Авторизация**. Экраны регистрации и аутентификаци, логика работы авторизованной и неавторизованной зоны. Определение политик доступов и прав.
2. **Профиль**. Блок профиля, функционал его редактирования. Модальные окна создания/редактирования профиля. Любой функцинал, связанный с профилем пользователя
3. **Посты**. Список карточек, загрузка, отображение, действия с карточками. Блок создания новой карточки.
4. **Хост-приложение**. Основное приложение, содержит layout, routing и включает в себя все остальные микрофронты. На базе хост приложения разворачивается шина событий.

#### Шина событий

Можно использовать **паттерн Pub/Sub** для независимого взаимодействия между микрофронтендами, используя контракт, основанный на событиях.


#### Фреймворк

Для большей технической свободы можно использовать SingleSPA. Каждая команда может заниматься разработкой любого javascript приложения, используя любой стек технологий.

## 2 часть

Как уже определили в 1 части, мы будем иметь 4 независимых приложения.

1. **Авторизация**.
2. **Профиль**.
3. **Посты**.
4. **Хост-приложение**.

Кроме того, все приложения будут переиспользовать следующий код:

1. **UI-kit** - Набор готовых ui компонентов. Предпочтительнее использовать корпоративный npm registry в случае, если микрофронтенды будут в разных репозиториях или как отдельный модуль в рамках монорепы.
2. **Шина событий** - объект в глобальном объекте, имплементирующий паттерн **pubsub**. реализуется в рамках хост приложения, важно иметь имплементацию для окружения тестов.
